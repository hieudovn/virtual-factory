## 3. C1–C12 confirmations

### C1 — Transport envelope — **PASS**

The serialized `ProjectedMessage` has a stable envelope across all 4 message
types: `message_key`, `projection_id` (`"mes"`), `message_type`,
`schema_name` (`vf.mes.*`), `schema_version` (`"1.0"`), `headers`
(`correlation_id`, `causation_id`), `payload` (dict). The MES proposal's
field names match the accepted serializer (`message_key` is the top-level key,
not `key`).

### C2 — `message_key` as idempotency identity — **PASS** (safe as `external_event_id`)

`message_key` == envelope `idempotency_key` ==
`run_id|source_event_id|point_id|schema_version`.

- Unique per logical fact **and per attempt** (quality `record_id` `QR-0002`
  FAIL vs `QR-0003` PASS → distinct keys).
- Stable across repeated polls (per-gateway delivery checkpoint).
- Changes across a reset only because `run_id` generation bumps exactly once.
- Late discovery reproduces the identical key (domain-derived, not wall-clock).

MES may safely use `message_key` as `external_event_id` under
`(source_system, external_event_id)`.

### C3 — `run_id` / reset semantics — **PASS**

`run_id` = `sub_line_id:R<generation>` (e.g. `ASSY-SL01:R1`). Generation bumps
exactly once per reset (M6-INT-01-C01 DEFECT A). A reset yields a fresh
`message_key` namespace; there is no collision with the prior run.

### C4 — `observation_id` semantics — **PASS** (audit/reference only)

`observation_id` is a random UUID4 generated per observation envelope. It is
practically globally unique but **not** source-event-derived and **not** stable
across re-emission / late-discovery / bridge restart. MES must use
`message_key` for idempotency and treat `observation_id` as audit/reference.

### C5 — `station_id` presence — **PARTIAL / ISSUE** (present, but not globally unique)

`station_id` is present in every P0 payload (`PRE-ASSY`, `AP01`…`AP11`).
However it is the TIPA station code, **identical across all 6 sub-lines**
(`ASSY-SL01`…`ASSY-SL06`). The MES proposal's station-only mapping
(`canonical.identity.map external_code = station_id`) is ambiguous. See C11.

### C6 — `subject_id` semantics — **PASS with clarification**

`subject_type` is always `"wip"`; `subject_id` is the VF WIP id. Not every
subject is a finished motor (`SSO2-*`/`RSO2-*` are upstream material WIPs;
`MTR-*` post-join). MES must resolve `subject_id` as a stable external WIP
code (best-effort), not assume a finished serial.

### C7 — AP04 genealogy payload — **PASS**

One `mes.genealogy_relationship` message carries **both** parents in the
`parent_wip_ids` list, the child in `child_wip_id`, `relationship_type` =
`assembly_join`, station `AP04`. Idempotency key is per child WIP. MES
expands one message into two parent→child relations but dedups on the single
message_key.

### C8 — Quality per-attempt identity — **PASS**

Every quality attempt has a distinct `record_id` (`QR-0002` FAIL attempt 1 vs
`QR-0003` PASS attempt 2) → distinct `message_key`. Disposition vocabulary:
`PASS`/`FAIL` (AP06 TEST), `NG`/`PASS` (AP08 VISUAL_INSPECTION), `PASS`
(AP11 FINAL_QC). `attempt_number` is present.

### C9 — AP11 FINAL_QC PASS vs RELEASE — **PASS**

Two distinct facts with distinct identities:
- FINAL_QC PASS → `mes.quality_result`, `event_type` `AP11_FINAL_QC_PASS`,
  source id `QR-0011`.
- RELEASE → `mes.release`, `event_type` `AP11_RELEASE`, source id
  `release:MTR-0001`, authoritative `release_time_s`.

VF release is evidence-only; it does not complete any MES MO/WO.

### C10 — Time semantics — **PASS**

`simulation_time_s` (Float) is present in every payload and is the
authoritative simulation occurrence order. `occurred_at` is **`null` in every
observed payload** (VF has no run epoch). No wall-clock timestamp is carried in
the payload (`emitted_at` is not propagated). MES receipt time must come from
its own `create_date`/`received_at`, and simulation seconds must never be
converted to a physical datetime.

### C11 — Sub-line isolation (the critical finding) — **ISSUE → MES-SIDE CORRECTION**

The 6 sub-lines share identical station codes and subject codes. The payload
does **not** carry `sub_line_id`, `production_line_id`, or `plant_id` as
first-class fields. The only first-class carrier of sub-line identity is
`run_id` (prefix before `":R"`).

Therefore the MES proposal's station-only mapping is **ambiguous** and must be
corrected to a composite binding `(sub_line_id, station_id)`.

### C12 — Decision

- **VF CONTRACT CHANGE REQUIRED: NO.** The consumer can already receive every
  required production fact from the accepted contract (`run_id` carries
  sub-line identity; all other fields are present and stable).
- **MES PROPOSAL CORRECTION REQUIRED: YES.** The station-only context-binding
  rule in proposal §4 is ambiguous across sub-lines and must become a
  composite `(sub_line_id, station_id)` binding.

## 5. Answers to the MES proposal's 5 questions (§13)

1. **Are `station_id`, `subject_id`, `simulation_time_s`, `occurred_at`
   guaranteed present and stable in every P0 payload?** — Yes for
   `station_id`, `subject_id` (as `subject_type`+`subject_id`),
   `simulation_time_s`. `occurred_at` is present but always `null` in the
   current VF (no run epoch); treat as optional/audit.
2. **Exact semantics of `run_id` across resets — is the idempotency key unique
   across runs?** — `run_id` = `sub_line_id:R<generation>`; generation bumps
   exactly once per reset. Idempotency key is unique across runs because it
   embeds `run_id`.
3. **Is `observation_id` globally unique or only unique within a run?** —
   UUID4, practically globally unique, but not source-stable; use
   `message_key` for idempotency, `observation_id` for audit only.
4. **Which payload fields carry parent and child identifiers for
   `mes.genealogy_relationship`?** — `child_wip_id` (child) and
   `parent_wip_ids` (list of parents); `wip_id` mirrors the child;
   `relationship_type` = `assembly_join`.
5. **Is `message_key` guaranteed unique per logical fact, including per-attempt
   for quality?** — Yes. FAIL attempt 1 and PASS attempt 2 have distinct
   `record_id` → distinct keys (verified `QR-0002` vs `QR-0003`).

| OPTIONAL ENRICHMENT (VF, future) | `sub_line_id`/`production_line_id`/`plant_id` not first-class in payload | VF may add these as first-class fields in a future, separately-gated slice; NOT required now |
