## 2. Sole objective

A canonical TIPA session `reset` must clear the **ASSY domain hold/freeze state**.

Before this correction, `AssyExecutionBridge.reset(...)` reset the runtimes and
re-prepared their run state, but kept the bridge's held sub-line set. A session
that had one line held/frozen therefore stayed partially frozen after
`RuntimeSession.reset()`: the next coordination window silently skipped the held
line instead of restoring the full six-line session baseline.

## 3. Change (exactly one production edit)

`src/virtual_factory/runcontrol/assy_bridge.py` — `reset(scope_ids)`:

```python
self._held_sub_line_ids.difference_update(scope_ids)
for sid in tuple(scope_ids):
    self._federation.reset_sub_line(sid)
```

- **Capability-scoped by construction**: reset clears the hold state of exactly
  the scopes it resets. A canonical session reset resets all six effective
  scopes, so it clears every domain hold (`held_sub_line_ids == ()`); a
  single-scope reset only clears that scope's hold. This reuses the existing
  capability-scoped reset contract rather than inventing a new session-wide
  lifecycle rule.
- **No G22 lifecycle change**: `RunLifecycleService.reset` is untouched; the
  same-run-id semantics (same run identity, same runtime objects, `last_time_s`
  back to 0, trace cleared) are unchanged.
- **No new architecture**: the hold/freeze seam is still a domain bridge
  capability; no generic coordinator/synchronization policy was added.

Test added to `tests/test_vnext_r1_production_semantics.py` (R1 module, now 40
tests): `TestHoldFreezeIndependence::test_session_reset_clears_domain_hold_state`.
