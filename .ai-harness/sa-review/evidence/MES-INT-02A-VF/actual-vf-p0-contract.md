## 3. Idempotency key (message_key) — exact derivation

`message_key` == envelope `idempotency_key` ==
`f"{run_id}|{source_event_id}|{point_id}|{schema_version}"`.

Real examples observed:

| Fact | message_key |
|---|---|
| Operation completion (PRE-ASSY, sub 1) | `ASSY-SL01:R1\|EXEC-00001\|assy.operation_completion\|1.0` |
| AP04 genealogy (child MTR-0001) | `ASSY-SL01:R1\|MTR-0001\|assy.ap04_genealogy\|1.0` |
| AP06 PASS attempt 1 (sub 1) | `ASSY-SL01:R1\|QR-0001\|assy.quality_result\|1.0` |
| AP06 FAIL attempt 1 (sub 3) | `ASSY-SL03:R1\|QR-0002\|assy.quality_result\|1.0` |
| AP06 PASS attempt 2 (sub 3) | `ASSY-SL03:R1\|QR-0003\|assy.quality_result\|1.0` |
| AP08 NG attempt 1 (sub 2) | `ASSY-SL02:R1\|QR-0006\|assy.quality_result\|1.0` |
| AP08 PASS attempt 2 (sub 2) | `ASSY-SL02:R1\|QR-0007\|assy.quality_result\|1.0` |
| AP11 final-QC PASS (sub 1) | `ASSY-SL01:R1\|QR-0011\|assy.ap11_final_qc\|1.0` |
| AP11 RELEASE (sub 1) | `ASSY-SL01:R1\|release:MTR-0001\|assy.ap11_release\|1.0` |

Properties (verified by M6-INT-01 + C01 tests):
- Unique per logical fact **and per attempt** (quality `record_id` is
  per-attempt: `QR-0002` FAIL vs `QR-0003` PASS).
- Stable across repeated `poll()` (delivery checkpoint dedups on
  `(run_id, source_event_id, gateway_id)`).
- Changes across a process reset because `run_id` generation bumps exactly
  once per reset (`ASSY-SL01:R1` → `ASSY-SL01:R2`); no stale-run collision.
- Late discovery reproduces the same key (derived from domain source ids, not
  from wall clock).

## 4. run_id semantics

`run_id` == `f"{sub_line_id}:R{generation}"` (e.g. `ASSY-SL01:R1`).
`generation` bumps exactly once per reset (sim-time regression guard,
M6-INT-01-C01 defect A). A reset therefore yields a **fresh message_key
namespace**; it does not collide with the prior run's keys.

---

## 5. observation_id semantics

`observation_id` is a **random UUID4**, generated once per `ObservationEnvelope`
at build time. It is:
- practically globally unique (UUID4), but
- **not** source-event-derived, and **not** stable across a re-emission /
  late-discovery / bridge restart of the same logical fact.

MES MUST use `message_key` (idempotency key) as the idempotency identity, and
treat `observation_id` as audit/reference only.

---

## 6. station_id semantics (sub-line isolation — the critical finding)

`payload.station_id` is **present in all 4 message classes**:
`PRE-ASSY`, `AP01`…`AP11`.

However, `station_id` is the **TIPA station code, identical across all 6
sub-lines** (`ASSY-SL01`…`ASSY-SL06`). A station-only mapping is ambiguous:
`AP06` exists on every sub-line. Same for `subject_id` (`MTR-0001` repeats on
every sub-line).

What is actually in the payload for disambiguation:
- `run_id` is first-class and embeds `sub_line_id` (`ASSY-SL03` from
  `ASSY-SL03:R1`).
- `sub_line_id` / `production_line_id` / `plant_id` are **NOT** first-class
  payload fields in the accepted serializer (they exist in the observation
  context but are not propagated by `MESProjection`).

Consequence for the consumer:
- MES **must** bind workstation context on the composite `(sub_line_id,
  station_id)`, not `station_id` alone.
- `sub_line_id` is currently recoverable only by parsing the `run_id` prefix
  before `":R"`.

---

## 7. subject_id semantics

`subject_type` == `"wip"` in all P0 messages. `subject_id` is the VF WIP id:
- operation completion: the WIP at the station (`SSO2-0001` pre-join,
  `MTR-0001` post-join),
- genealogy: the **child** WIP (`MTR-0001`),
- quality / release: the motor WIP (`MTR-xxxx`).

Not every `subject_id` is a finished motor serial (`SSO2-*` / `RSO2-*` are
upstream material WIPs). MES must treat `subject_id` as a stable external WIP
code (best-effort resolution), not assume `mes.wip.unit.finished_serial`.

## 11. Time semantics (real observation)

- `simulation_time_s` (Float) present in **every** payload — authoritative
  simulation occurrence order.
- `occurred_at` is **`null` in every observed payload** (VF has no run epoch).
  It is an optional envelope field, not a wall-clock emission time.
- No wall-clock timestamp is carried in the `ProjectedMessage` payload
  (`emitted_at` exists on the observation envelope but is not propagated).
  MES receipt time must come from its own `create_date`/`received_at`.

## 12. Fields guaranteed present in every P0 payload

`observation_id`, `idempotency_key`, `run_id`, `simulation_time_s`,
`occurred_at` (may be null), `subject_type`, `subject_id`, `station_id`,
`event_type`.

Type-specific: `execution_id`/`wip_id`/`operation_result`/`completion_mode`/
`attempt_number`/`source` (execution); `child_wip_id`/`parent_wip_ids`/
`component_ids`/`join_station`/`join_time_s`/`relationship_type`
(genealogy); `record_id`/`check_type`/`disposition`/`attempt_number`/
`reason_code` (quality); `release_time_s` (release).

Fields NOT present in the payload: `sub_line_id`, `production_line_id`,
`plant_id`, `emitted_at`.
